# Languages (English and Spanish)

The GMS speaks English and Spanish. Spanish is in **beta**: the switcher says "Español (beta)" until a
native speaker has reviewed the catalog (see [Reviewing and fixing the Spanish](#reviewing-and-fixing-the-spanish)).

**Translated:** the interface, emails, the fixed text of generated documents, the fixed text of public
pages, and share-card text.

**Not translated:**
- what people write (a funder's opportunity, forms and emails; an applicant's answers): it stays in the
  language it was written in;
- the CommonGrants and REST APIs, which are machine interfaces and stay English (`code` and `detail` of
  an error never change);
- MCP tool descriptions.

## How it fits together

| Piece | Where |
|---|---|
| Catalogs: one JSON file per language and namespace | `packages/i18n/catalogs/{en,es}/{namespace}.json` |
| Languages, the choice order, the cookie | `packages/i18n/src/locales.ts` |
| Formatting (ICU messages, numbers, money, dates) | `packages/i18n/src/translate.ts`, `src/intl.ts` |
| Web: the page's language, `useT`, the switch | `apps/web/src/i18n/` |
| Web build: catalogs precompiled, parser left out | `packages/i18n/src/vite.ts` (in `apps/web/vite.config.ts`) |
| Workers (emails, page meta): every catalog at once | `@gms/i18n/server` (`serverTranslator`) |
| The "no literal strings" lint rule and its file list | `eslint.i18n.js` |

The library is FormatJS's `intl-messageformat` (BSD-3-Clause): ICU MessageFormat, the same messages in
the browser and in Workers. Why it and not i18next or react-intl: `docs/decisions.md` (2026-11-16).

### Namespaces

| Namespace | What | Translated by |
|---|---|---|
| `public` | public pages, sign-in, onboarding, account, switch pages, gallery, landing | D2a |
| `shared` | `components/`, `app/`, `screens/shared/`, `lib/` labels (status names, buttons used everywhere) | D2a |
| `applicant` | `screens/applicant/`, the applicant parts of `forms/` | D2b |
| `funder` | `screens/funder/`, reviewer screens, form and report builders | D2c |
| `email` | `packages/notify` templates, documents' fixed text (`pdf.*`), share cards (`card.*`) | D2d |
| `errors` | user-facing API error messages (`detailLocalized`) | D2d |

Each catalog is a chunk of its own (`assets/i18n-<lang>-<namespace>-<hash>.js`), loaded only with the
screens of its area. English `shared` is the app shell's (components, status names, buttons used
everywhere), so it is preloaded with the first page. `public` loads with the public screens: every public
route is declared with `publicScreen()` in `app/App.tsx`, which fetches the screen and the catalog side by
side, and a screen elsewhere that shows a public screen's part (the gallery's parts, the embed card, the
"what we email you" card, the "Powered by" label) calls `usePublicMessages()` first
(`apps/web/test/i18n-public-catalog.test.ts` checks both). `applicant` and `funder` load with their screens.
An English visitor downloads nothing for Spanish. `email` and `errors` are read by Workers only
(`SERVER_ONLY_NAMESPACES` in `packages/i18n/src/vite.ts`): in the web build each is an empty catalog
with no short ids, so none of their text reaches a browser and their keys never meet the web app's.

The web build (`packages/i18n/src/vite.ts`) parses every message at build time (the browser never loads
the ICU parser), emits each catalog as one `JSON.parse("…")`, and replaces every key with a short id, in
the catalogs and in the code, so a key is not shipped twice. A key must be a string literal: a key built
at run time inside a translation call (`t(`step.${name}`)`, `t("step." + name)`) stops the build. Only the
translation calls' arguments are inspected (`TRANSLATION_CALLS`), so a file name such as
`applications.${format}` or a field path such as `stages.${i}.label` elsewhere is left alone. Every string
literal equal to a key is still shortened wherever it is (keys are also passed through label tables), so
data that looks like a key (a report column id such as `programs.name`) must not equal one.

`apps/web/test/bundle-size.test.ts` measures the English bundle against v1.10.0
(`build/bundle-baseline.json`): the first page grows by less than **40 KB gzipped**
(`FIRST_PAGE_BUDGET_BYTES`), everything an English visitor can download grows by less than **60 KB
gzipped** (`BUDGET_BYTES`; the screens' text moved into the catalogs), and each area's catalog is a chunk
of its own as above. At v1.11.0 they measured +22.6 KB and +47.3 KB. Re-measure the baseline only for a
change that is not about languages.

## Writing a message

Keys are flat and dotted by screen or component, camelCase segments: `signIn.email.label`,
`landing.hero.title`, `status.under_review`. The English file is the source: add the key there, then the
same key in Spanish. Keys are typed from the English file, so a key that does not exist is a type error.

Messages are [ICU MessageFormat](https://formatjs.github.io/docs/core-concepts/icu-syntax):

```json
{
  "dashboard.greeting": "Welcome back, {name}",
  "applications.count": "{count, plural, one {# application} other {# applications}}",
  "deadline.left": "{days, plural, =0 {Due today} one {# day left} other {# days left}}",
  "role.label": "{role, select, admin {Admin} reviewer {Reviewer} other {Member}}",
  "signIn.terms": "By signing in you accept the <link>terms of use</link>."
}
```

Rules:
- **Every string with a variable is one message with a placeholder.** Never build a sentence from pieces
  (`t("a") + name + t("b")`): word order differs between languages.
- **Plurals use the plural syntax**, never `count === 1 ? … : …`. Spanish has `one`, `many` (millions)
  and `other`; `other` covers `many` when a message leaves it out.
- **Links and emphasis inside a sentence are tags** (`<link>…</link>`, `<b>…</b>`) filled with `t.rich`.
- A literal `{`, `}` or `<` is quoted with apostrophes (`'{'`); a lone apostrophe ("don't") needs nothing.
- Money, dates and numbers are formatted with `Intl` in the active language (below) and passed in as
  placeholders. Spanish dates read "15 de noviembre de 2026"; dollars read "$50,000" in both languages.
- No text in images.
- Status is always icon plus label: translate the label, keep the icon.

## Using messages in the web app

```tsx
import { useT } from "../../i18n/index.tsx";

export default function SignIn() {
  const t = useT("public");
  const s = useT("shared");
  return (
    <>
      <h1>{t("signIn.title")}</h1>
      <p>{t("signIn.sent", { email })}</p>
      <p>{t.rich("signIn.terms", { link: (chunks) => <Link to="/terms">{chunks}</Link> })}</p>
      <button type="submit">{s("action.continue")}</button>
    </>
  );
}
```

- `useT(ns)` returns `t(key, values?)` (text) and `t.rich(key, values)` (elements). A namespace that is
  not loaded yet suspends the screen until it arrives (routes already render inside `Suspense`). Use it
  for `applicant` and `funder`.
- For `public` and `shared` (loaded before any screen that reads them renders) a file can also take one translator for the whole module:
  `const t = translator("public");` at the top, then `t("…")` in any function of the file, components
  and helpers alike. It reads the current language at each call; screens redraw on a change because
  the routes remount. The public and shared screens are written this way.
- The applicant screens (and the form renderer) take a module translator of their own:
  `import { t, useApplicantText } from "screens/applicant/i18n.ts"`. `t` reads the current language at
  each call like `translator("public")`; because `applicant` is loaded on demand, every screen's default
  export (and every component shown outside the applicant screens, such as `FormView`) calls
  `useApplicantText()` first, which suspends until the catalog is there. The names the applicant screens
  show for the vocabularies of `lib/outside.ts` and `lib/writeKeep.ts` (stages, moves, document types,
  go/no-go criteria, limits, milestones, months) come from `screens/applicant/labels.ts`; the lib tables
  keep their English names for code and tests.
- The form renderer translates only its own text (required marks, counters, buttons, address parts,
  validation). The funder's labels, help text and options are shown as written. Validation messages
  from `@gms/forms` are English; `FormView` shows each known one from the catalog (`form.error.*`, by
  its wording) and any other as written.
- Outside React (`lib/` helpers): `translate("shared", key, values)`.
- The funder and reviewer screens (`funder`) work the same way with `import { t } from "./i18n.ts"` in
  `screens/funder/`, and every component a route renders from there (and any one another screen borrows,
  such as `SettingsNav`) calls `useFunderMessages()` first: it suspends until the namespace is loaded.
  `t` itself never suspends, because it also runs in event handlers and in query callbacks after an
  `await`, where React's `use` must not run (a suspension there is lost: React error 459).
- **A table of labels is never a constant built once** (it would stay in the language the page loaded
  in): make it a function (`const STEPS = () => [t("…"), …]`), give its objects getters
  (`get label() { return t("…"); }`, as `STATUS` in `components/status.tsx`), or key it by id
  (`STEP_KEY[step]`, as in `ImportWizard.tsx`).
- **A label that is also an identity stays English.** The rail's items are named by their English label
  (`active="Dashboard"`, the roles' hidden items); `railLabel(label)` in `components/shells.tsx` is what
  the person reads. Keep passing English to `active`.
- **Keys are string literals.** The web build replaces every key with a short id (see below); a key built
  at run time (`` t(`step.${name}`) ``) stops the build with the file's name. Map ids to literal keys
  instead (`const STEP_KEY = { source: "importWizard.step.source", … } as const`).
- A sentence with a variable part is one message per variant, never a fragment passed in as a value:
  `t(verified ? "x.verified" : "x.notVerified")`, not `t("x", { state: verified ? "verified" : "…" })`.
  Separators between messages (` · `, a space) stay in the code (`` {cond && ` · ${t("…")}`} ``).
- A number placeholder is formatted with grouping (`1,234`); pass a year or an id as text
  (`{ year: String(year) }`).
- Dates and money: `formatDate`, `formatDateAs(iso, "medium")`, `formatMoney`, `formatMinor`,
  `formatAwardRange` in `lib/format.ts` follow the page's language. Code that calls `Intl` itself passes
  `intlLocale()` instead of `"en-US"`. `@gms/i18n` also has `formatNumber`, `formatCurrency`,
  `formatDateIn`, `formatDateTimeIn` and `formatList` taking an explicit language.
- On a language change the routes remount (`app/App.tsx`), so every screen draws again in the new
  language, including values it computed once. The session and the address are kept; unsaved typing on
  the screen is not.
- `useLocale()` gives the current language; `changeLocale(locale)` switches the page (the switcher and
  the saved preference call it; screens do not).

### Tests

- Web unit tests start in English with every English catalog loaded (`test/setup.ts`). A test that needs
  Spanish calls `await changeLocale("es")` (from `src/i18n/current.ts`) before rendering; it is put back
  to English after each test.
- End-to-end in Spanish: set the cookie before the first page, e.g.
  `await context.addCookies([{ name: "gms_lang", value: "es", url: baseURL }])`, or open a public page
  with `?lang=es`. `e2e/i18n-spanish.spec.ts` is the smoke flow.
- `e2e/a11y-every-route.spec.ts` runs every route in English (four combinations) and again in Spanish
  (desktop and phone, light). A route's `steps` that name controls must name them in both languages
  (see `SIGN_IN` in `e2e/a11y-routes.ts`): when you translate a screen a step clicks through, change its
  names to a regular expression with both.

## Using messages in Workers

```ts
import { serverTranslator } from "@gms/i18n/server";
const t = serverTranslator(locale, "email");
const subject = t("award.subject", { program });
```

`@gms/i18n/server` imports every catalog statically: right for Workers, wrong for the web app (it would
put Spanish in every English visitor's download). The web app imports `@gms/i18n` and `apps/web/src/i18n`.

## Choosing the language

In this order (`chooseLocale` in `packages/i18n/src/locales.ts`, one function for the browser, the front
Worker and the API):

1. a signed-in person's saved preference;
2. `?lang=es` (or `en`) on the address;
3. the `gms_lang` cookie (set by the switcher; a year, `SameSite=Lax`, the whole site);
4. the browser's languages (`Accept-Language` on a server, `navigator.languages` in the browser);
5. English.

`<html lang>` follows the active language. A value the GMS does not speak is skipped, never an error.

- **Signed in:** `GET /gms/me` returns `locale` (`"en"`, `"es"` or `null`), `PUT /gms/me/preferences`
  `{ locale }` saves it (a signed-in person only; agents and API clients are refused), stored in
  `user_preferences` (migration 0043). The switcher saves it; the app applies it when the person loads
  (`LocaleFromPreference`) and copies it into the cookie so the next visit starts in it.
- **Switchers:** the footer of every public page (landing, funder and opportunity pages, grants awarded,
  switch pages, gallery, agents), the sign-in page, the account menu (workspace button) and the phone
  menu. After a switch, focus returns to the control that made it.
- **Emails** go in the recipient's language (below, "Emails, documents and errors").
- **Page meta (front Worker):** a public page asked for with `?lang=es` gets its title, description and
  image text in Spanish and `<html lang="es">`; every public page lists `hreflang` alternates (`en`, `es`,
  `x-default` = English) with a canonical address per language (`apps/web/src/edge/meta.ts`). Its share
  card is asked for with the same language (`/og/….png?lang=es&v=…`) and drawn with Spanish fixed words.

## Emails, documents and errors

Every email's fixed words are in the `email` catalog; each builder in `packages/notify` takes the
recipient's `locale` (English when absent) and writes dates as the language does (Spanish spells them
out; English keeps the `YYYY-MM-DD` the GMS has always printed). What people wrote stays as written.

| Who reads it | Its language |
|---|---|
| A person with an account | their saved preference (`recipientLocale(s)` in `apps/api/src/services/preferences.ts`); English without one, or when the store cannot be read |
| An invited address (workspace, reviewer, draft and award invitations) | the preference of the account with that address (`addressLocale`, `apps/api/src/services/recipient-locale.ts`); English for a new address |
| An organization's own address (its Passport record's) | its admins' language when they all chose the same one, English otherwise (`memberAddressLocales`) |
| The person filling the switch page's migration form | the language they filled it in (the request's) |
| OpenGrants staff (consulting and migration requests) | English, always |

- **Built-in letters** (receipt, revision request, decline, award, report reminder, payment): the
  default copy is the catalog's (`letter.*`, merge fields written `{recipient_name}` and turned back into
  `{{recipient.name}}`); a funder's edited template is sent as written, in whatever language it was
  written, without a `lang`. `sendLetter` sends one email per language, English first, so an
  organization whose people all read English gets the one email it always did. The receipt's "Powered
  by" line follows the recipient.
- **Member notices and jobs:** `mailMembers` takes `localized: (locale) => ({ subject, text, html? })`
  and writes each member in their language; `OutboundEmail.locale` sets the HTML document's `lang` (set it
  only when the content really is in that language). The jobs Worker reads preferences through
  `SupabasePreferences` in its ports. The daily and weekly digests translate their frame; the in-app
  notification lines they list are the API's own (English) text.
- **Documents:** the board docket and the send package (PDF, `answers.txt`, its email) print their fixed
  labels in the requester's language: `ServiceContext.locale`, read from the request (`?lang=`, the
  `gms_lang` cookie, `Accept-Language`; `apps/api/src/lib/locale.ts`). `renderPdf` takes `pageLabel` and
  `lang`. Agreements and award letters are re-rendered to verify stored hashes, so their fixed text is
  unchanged (English).
- **Errors:** a request to a GMS route (`/gms/…`) in Spanish gets `detailLocalized` beside the code in
  `errors[0]`, when the code is in the `errors` catalog (`code.<code>`, and `notFound.<resource>` for a
  not-found error naming what was not found). `code` and the English `message` never change; the
  CommonGrants routes, OAuth and MCP never carry it. The web app's `ApiError` shows `detailLocalized`,
  else the English, and keeps the English as `detail`. `apps/api/test/i18n-errors.test.ts` counts the
  codes the API raises and requires the 80 most common in the catalog: add a code's message there when
  you add a code.

## The lint rule

`i18n/no-literal-strings` (in `eslint.i18n.js`) reports text in JSX, string literals a JSX child would
show (`{"Save"}`, `{busy ? "Saving…" : "Save"}`), and literals in attributes a person reads or hears
(`aria-label`, `alt`, `title`, `placeholder`, `label`, and props ending in `Label`, `Title`, `Text`,
`Placeholder`, `Hint`, `Help`, `Message`, `Description`, `Heading`, `Caption`). Code inside `<code>`,
`<kbd>`, `<pre>` and `<samp>`, punctuation, and product names (OpenGrants, Passport, CommonGrants…) are
allowed. It applies to the files in `TRANSLATED` in `eslint.i18n.js`: **add your directories there once
every string in them is a message.** It cannot see strings built outside JSX (a `setError("…")`): those
need a message too.

## Catalog checks

`packages/i18n/test/catalogs.test.ts` runs on every namespace:

- every English key has a Spanish value, and Spanish has no extra keys;
- no value is empty;
- no Spanish value is identical to the English one, unless it has no words (`{name} · {role}`) or is on
  the list in `packages/i18n/catalogs/same-as-english.json` (product names, formats known by name; add a
  whole key under `keys` only when the Spanish truly reads the same);
- both languages are valid ICU with the same placeholders, plurals and tags;
- the Spanish keeps to the glossary (words it rules out, such as "aplicación" for application).

## Spanish style

- Neutral Latin American Spanish, addressing the person as **usted** ("Inicie sesión", "Revise su
  solicitud"), plain and warm, written for nonprofits in the US and Latin America.
- Never machine-literal: say it the way a program officer in Los Angeles or Bogotá would.
- Sentence case for titles and buttons ("Crear una convocatoria", not "Crear Una Convocatoria").
- Buttons and links are verbs in the infinitive or the usted imperative, the same within a screen:
  "Guardar", "Enviar solicitud", "Iniciar sesión".
- Prefer inclusive forms that read naturally: "revisor(a)" where the glossary says so, or a neutral noun
  ("el equipo de revisión", "la persona solicitante") where one fits.
- Product names are not translated: OpenGrants, Passport, CommonGrants, OpenGrants Grant Management System.

## Reviewing and fixing the Spanish

The Spanish catalog was written carefully against the glossary, but **a native speaker should review
it** before "(beta)" comes off the switcher. To review or fix a translation:

1. Find the message: search `packages/i18n/catalogs/es/*.json` for the Spanish text you saw (or the
   English one in `catalogs/en/` for its key).
2. Edit the Spanish value. Keep every `{placeholder}`, plural (`{count, plural, …}`) and `<tag>` as it is
   in English; change only the words around them.
3. Run `pnpm --filter @gms/i18n test` (the catalog checks) and, for a screen, `pnpm --filter @gms/web test`.
4. Open a pull request titled `fix(i18n): …`, saying what read wrong and why the new wording is better.
   A new term goes into the glossary above in the same pull request.

Adding a language: add its code to `LOCALES`, `INTL_LOCALE` and `LANGUAGE_NAMES` in `locales.ts`, a
folder under `catalogs/` with every namespace, its loaders in `catalogs.ts` and `server.ts`, and its
alternate in the page meta (`apps/web/src/edge/meta.ts`).

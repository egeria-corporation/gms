# Languages (English and Spanish)

The GMS speaks English and Spanish. Spanish is in **beta**: the switcher says "Español (beta)" until a
native speaker has reviewed the catalog (see [Reviewing and fixing the Spanish](#reviewing-and-fixing-the-spanish)).

**Translated:** the interface, emails, the fixed text of generated documents, the fixed text of public
pages, and share-card text.

**Not translated:**
- what people write (a funder's opportunity, forms and emails; an applicant's answers): it stays in the
  language it was written in;
- the CommonGrants and REST APIs, which are machine interfaces and stay English (`code` and `detail` of
  an error never change);
- MCP tool descriptions.

## How it fits together

| Piece | Where |
|---|---|
| Catalogs: one JSON file per language and namespace | `packages/i18n/catalogs/{en,es}/{namespace}.json` |
| Languages, the choice order, the cookie | `packages/i18n/src/locales.ts` |
| Formatting (ICU messages, numbers, money, dates) | `packages/i18n/src/translate.ts`, `src/intl.ts` |
| Web: the page's language, `useT`, the switch | `apps/web/src/i18n/` |
| Web build: catalogs precompiled, parser left out | `packages/i18n/src/vite.ts` (in `apps/web/vite.config.ts`) |
| Workers (emails, page meta): every catalog at once | `@gms/i18n/server` (`serverTranslator`) |
| The "no literal strings" lint rule and its file list | `eslint.i18n.js` |

The library is FormatJS's `intl-messageformat` (BSD-3-Clause): ICU MessageFormat, the same messages in
the browser and in Workers. Why it and not i18next or react-intl: `docs/decisions.md` (2026-11-16).

### Namespaces

| Namespace | What | Translated by |
|---|---|---|
| `public` | public pages, sign-in, onboarding, account, switch pages, gallery, landing | D2a |
| `shared` | `components/`, `app/`, `screens/shared/`, `lib/` labels (status names, buttons used everywhere) | D2a |
| `applicant` | `screens/applicant/`, the applicant parts of `forms/` | D2b |
| `funder` | `screens/funder/`, reviewer screens, form and report builders | D2c |
| `email` | `packages/notify` templates, documents' fixed text, share cards | D2d |
| `errors` | user-facing API error messages (`detailLocalized`) | D2d |

English `public` and `shared` ship in the first bundle. Every other catalog, and all of Spanish, is a
separate chunk (`assets/i18n-<lang>-<namespace>-<hash>.js`) loaded when first needed, so an English
visitor downloads nothing for Spanish. `apps/web/test/bundle-size.test.ts` holds the growth of the
English bundle from this work under 15 KB gzipped.

## Writing a message

Keys are flat and dotted by screen or component, camelCase segments: `signIn.email.label`,
`landing.hero.title`, `status.under_review`. The English file is the source: add the key there, then the
same key in Spanish. Keys are typed from the English file, so a key that does not exist is a type error.

Messages are [ICU MessageFormat](https://formatjs.github.io/docs/core-concepts/icu-syntax):

```json
{
  "dashboard.greeting": "Welcome back, {name}",
  "applications.count": "{count, plural, one {# application} other {# applications}}",
  "deadline.left": "{days, plural, =0 {Due today} one {# day left} other {# days left}}",
  "role.label": "{role, select, admin {Admin} reviewer {Reviewer} other {Member}}",
  "signIn.terms": "By signing in you accept the <link>terms of use</link>."
}
```

Rules:
- **Every string with a variable is one message with a placeholder.** Never build a sentence from pieces
  (`t("a") + name + t("b")`): word order differs between languages.
- **Plurals use the plural syntax**, never `count === 1 ? … : …`. Spanish has `one`, `many` (millions)
  and `other`; `other` covers `many` when a message leaves it out.
- **Links and emphasis inside a sentence are tags** (`<link>…</link>`, `<b>…</b>`) filled with `t.rich`.
- A literal `{`, `}` or `<` is quoted with apostrophes (`'{'`); a lone apostrophe ("don't") needs nothing.
- Money, dates and numbers are formatted with `Intl` in the active language (below) and passed in as
  placeholders. Spanish dates read "15 de noviembre de 2026"; dollars read "$50,000" in both languages.
- No text in images.
- Status is always icon plus label: translate the label, keep the icon.

## Using messages in the web app

```tsx
import { useT } from "../../i18n/index.tsx";

export default function SignIn() {
  const t = useT("public");
  const s = useT("shared");
  return (
    <>
      <h1>{t("signIn.title")}</h1>
      <p>{t("signIn.sent", { email })}</p>
      <p>{t.rich("signIn.terms", { link: (chunks) => <Link to="/terms">{chunks}</Link> })}</p>
      <button type="submit">{s("action.continue")}</button>
    </>
  );
}
```

- `useT(ns)` returns `t(key, values?)` (text) and `t.rich(key, values)` (elements). A namespace that is
  not loaded yet suspends the screen until it arrives (routes already render inside `Suspense`).
- Outside a component (label tables, `lib/` helpers): `translate("shared", key, values)`, for `public` and
  `shared` only (always loaded). A table of labels becomes a function or getters, not a constant built
  once: see `APPLICANT_TYPE_LABELS` in `apps/web/src/lib/format.ts`.
- Dates and money: `formatDate`, `formatDateAs(iso, "medium")`, `formatMoney`, `formatMinor`,
  `formatAwardRange` in `lib/format.ts` follow the page's language. Code that calls `Intl` itself passes
  `intlLocale()` instead of `"en-US"`. `@gms/i18n` also has `formatNumber`, `formatCurrency`,
  `formatDateIn`, `formatDateTimeIn` and `formatList` taking an explicit language.
- On a language change the routes remount (`app/App.tsx`), so every screen draws again in the new
  language, including values it computed once. The session and the address are kept; unsaved typing on
  the screen is not.
- `useLocale()` gives the current language; `changeLocale(locale)` switches the page (the switcher and
  the saved preference call it; screens do not).

### Tests

- Web unit tests start in English with every English catalog loaded (`test/setup.ts`). A test that needs
  Spanish calls `await changeLocale("es")` (from `src/i18n/current.ts`) before rendering; it is put back
  to English after each test.
- End-to-end in Spanish: set the cookie before the first page, e.g.
  `await context.addCookies([{ name: "gms_lang", value: "es", url: baseURL }])`, or open a public page
  with `?lang=es`.

## Using messages in Workers

```ts
import { serverTranslator } from "@gms/i18n/server";
const t = serverTranslator(locale, "email");
const subject = t("award.subject", { program });
```

`@gms/i18n/server` imports every catalog statically: right for Workers, wrong for the web app (it would
put Spanish in every English visitor's download). The web app imports `@gms/i18n` and `apps/web/src/i18n`.

## Choosing the language

In this order (`chooseLocale` in `packages/i18n/src/locales.ts`, one function for the browser, the front
Worker and the API):

1. a signed-in person's saved preference;
2. `?lang=es` (or `en`) on the address;
3. the `gms_lang` cookie (set by the switcher; a year, `SameSite=Lax`, the whole site);
4. the browser's languages (`Accept-Language` on a server, `navigator.languages` in the browser);
5. English.

`<html lang>` follows the active language. A value the GMS does not speak is skipped, never an error.

## The lint rule

`i18n/no-literal-strings` (in `eslint.i18n.js`) reports text in JSX, string literals a JSX child would
show (`{"Save"}`, `{busy ? "Saving…" : "Save"}`), and literals in attributes a person reads or hears
(`aria-label`, `alt`, `title`, `placeholder`, `label`, and props ending in `Label`, `Title`, `Text`,
`Placeholder`, `Hint`, `Help`, `Message`, `Description`, `Heading`, `Caption`). Code inside `<code>`,
`<kbd>`, `<pre>` and `<samp>`, punctuation, and product names (OpenGrants, Passport, CommonGrants…) are
allowed. It applies to the files in `TRANSLATED` in `eslint.i18n.js`: **add your directories there once
every string in them is a message.** It cannot see strings built outside JSX (a `setError("…")`): those
need a message too.

## Catalog checks

`packages/i18n/test/catalogs.test.ts` runs on every namespace:

- every English key has a Spanish value, and Spanish has no extra keys;
- no value is empty;
- no Spanish value is identical to the English one, unless it has no words (`{name} · {role}`) or is on
  the list in `packages/i18n/catalogs/same-as-english.json` (product names, formats known by name; add a
  whole key under `keys` only when the Spanish truly reads the same);
- both languages are valid ICU with the same placeholders, plurals and tags;
- the Spanish keeps to the glossary (words it rules out, such as "aplicación" for application).

## Spanish style

- Neutral Latin American Spanish, addressing the person as **usted** ("Inicie sesión", "Revise su
  solicitud"), plain and warm, written for nonprofits in the US and Latin America.
- Never machine-literal: say it the way a program officer in Los Angeles or Bogotá would.
- Sentence case for titles and buttons ("Crear una convocatoria", not "Crear Una Convocatoria").
- Buttons and links are verbs in the infinitive or the usted imperative, the same within a screen:
  "Guardar", "Enviar solicitud", "Iniciar sesión".
- Prefer inclusive forms that read naturally: "revisor(a)" where the glossary says so, or a neutral noun
  ("el equipo de revisión", "la persona solicitante") where one fits.
- Product names are not translated: OpenGrants, Passport, CommonGrants, OpenGrants Grant Management System.

## Reviewing and fixing the Spanish

The Spanish catalog was written carefully against the glossary, but **a native speaker should review
it** before "(beta)" comes off the switcher. To review or fix a translation:

1. Find the message: search `packages/i18n/catalogs/es/*.json` for the Spanish text you saw (or the
   English one in `catalogs/en/` for its key).
2. Edit the Spanish value. Keep every `{placeholder}`, plural (`{count, plural, …}`) and `<tag>` as it is
   in English; change only the words around them.
3. Run `pnpm --filter @gms/i18n test` (the catalog checks) and, for a screen, `pnpm --filter @gms/web test`.
4. Open a pull request titled `fix(i18n): …`, saying what read wrong and why the new wording is better.
   A new term goes into the glossary above in the same pull request.

Adding a language: add its code to `LOCALES`, `INTL_LOCALE` and `LANGUAGE_NAMES` in `locales.ts`, a
folder under `catalogs/` with every namespace, its loaders in `catalogs.ts` and `server.ts`, and its
alternate in the page meta (`apps/web/src/edge/meta.ts`).

- 2026-11-10 · The GMS client at Passport is to be owned by Egeria Corporation · owner decision. Not done yet: Passport has no organizations, so Egeria Corporation must be claimed there first.

- 2026-11-11 · **Sign in with Passport** (`GET /gms/passport/signin/start` and `/callback`): one trip to Passport signs the person in (OpenID Connect, `openid email`) and links the organization they approve · owner decision; "Continue with Passport" used to be a link to a page that needs a session, so it did nothing for a signed-out visitor. Email-code sign-in is unchanged.
- 2026-11-11 · A Passport sign-in whose verified email matches an existing GMS account signs in to that account · owner decision. Email is already the account key here (the email code proves the same control), so the GMS selects the account by the email Passport marks verified and keeps the Passport user id in the account's `app_metadata.passport_user_id` for reference; it is never used to select an account.
- 2026-11-11 · The callback trusts nothing from the browser: PKCE verifier, nonce and a browser-binding value are sealed in `state` (AES-GCM, `CREDENTIALS_ENCRYPTION_KEY`, ten minutes); the binding must equal a `__Host-` HttpOnly SameSite=Lax cookie set at the start, so a callback URL planted in another browser is refused (login CSRF); the ID token is verified with `jose` against Passport's published keys for issuer, audience (the GMS client), expiry and nonce. Every failure redirects to `/signin?passport_error=<code>` with one of seven codes and no detail.
- 2026-11-11 · The session itself is still Supabase Auth's: after the checks the API asks the Supabase admin API for a one-time magic-link token and redirects to `/auth/passport#token_hash=…`, which the web app redeems with `verifyOtp` · no second session system, and MFA, sessions list and sign-out keep working. The token travels in the URL fragment, which is not sent to servers or logged; the response is `no-store` with `Referrer-Policy: no-referrer`.
- 2026-11-11 · A new person who approves no organization at Passport is not given an account: they are sent back with `no_organization` and a link to claim one. A person who already belongs to a workspace is signed in without linking · applying starts from an organization's record, and an account with nothing to open helps nobody.
- 2026-11-11 · Both sign-in routes share a fixed-window limit of 30 requests per network address per ten minutes (the KV namespace the MCP limiter uses) · they are public and each one makes Passport or Supabase do work.
- 2026-11-11 · The applicant organization link (`linkApplicantOrganization`) is one function used by the consent callback and the sign-in callback · two copies would drift. Identity scopes are never written to `passport_links.scopes`.
- 2026-11-11 · **Accounts have no passwords, and nothing set before an email was proven survives the proof** (migration `0017`, security review). Supabase Auth lets anyone start a sign-up for any address with a password; the account stays unconfirmed, but the password stayed on it and began working once the real owner proved the email by code, magic link or Passport (verified on the hosted project). The GMS only ever signs people in by emailed code or Passport, so a trigger on `auth.users` clears the password on every insert and update, and a second one removes any second factor and session at the moment an email is first confirmed. Both run as the role changing the row (Supabase Auth's own), so they need no extra grant. "Confirm email" must stay on in Supabase Auth (it is on for the hosted project; `supabase/config.toml` and `docs/self-host.md` said off and are corrected): with it off a sign-up is handed a session for an unproven address at once, which no trigger can tell apart from a real one.
- 2026-11-11 · Sign in with Passport **replaces an unconfirmed account instead of adopting it** (deleted, then created fresh and confirmed; if it cannot be deleted nobody is signed in), and **ties an account to the first Passport user that signs in to it**: `app_metadata.passport_user_id` is written once and a different Passport user presenting the same verified email is refused with `passport_error=account_mismatch`. This narrows the owner's "same email, same account" rule to accounts whose email was proven here; email-code sign-in still works for anyone refused.
- 2026-11-11 · **The last hop of Sign in with Passport is bound to the tab that started it.** The button stores a random value in `sessionStorage` and sends it as `hop`; the API seals it in `state` and returns it in the fragment beside the one-time sign-in; `/auth/passport` redeems only when the two match, uses the value up either way, and never redeems in a tab that is already signed in. Without this a link carrying an attacker's own one-time sign-in would silently sign a victim's browser into the attacker's account. A start request without a valid `hop` is refused, so the API's start route cannot be used on its own.
- 2026-11-11 · ID tokens must carry `typ: JWT`, and when Passport's key set names any `oauth-…` key only those keys are used, so no other kind of Passport token or key family can pass as a sign-in. An unknown key id refetches the set once (key rotation). The web app's destination check is the API's allow-list (`RETURN_TO`), held equal by a test. Start and callback are rate-limited apart, per address (`CF-Connecting-IP`, else the first forwarded address); requests with no address share one larger allowance. KV has no atomic increment, so the limit is a brake, not a quota. Not changed: Supabase's one-time token lifetime (an hour, project setting).

- 2026-11-11 · **Passport's authenticator is accepted as this app's second step** (owner's decision). A person who signs in through Passport, whose ID token says `acr: aal2` with `mfa` among the methods, is not asked for the GMS's own authenticator. The callback records that against the SHA-256 of the one-time sign-in token; the web app redeems the token for a session and presents it once more (`POST /gms/passport/signin/second-step`); the record is bound to that session's id, once. Only that session counts as verified. An email-code session never holds the token, a second session of the same person does not inherit it, and the record alone gives no access. Migration 0018 (`passport_second_steps`, service role only).
- 2026-11-11 · The trust lasts **twelve hours from when the person passed Passport's authenticator** (`auth_time`), not from when the GMS session started, and the record must be claimed within ten minutes of the sign-in. An ID token without `auth_time`, or with one more than twelve hours old or in the future, records nothing. Ending the session removes the record (foreign key to `auth.sessions`). The directive allowed `min(auth_time + 12 h, session lifetime)`; the session's lifetime is Supabase's to decide and the row goes with the session, so only the first term is stored.
- 2026-11-11 · **One rule for the second step.** `secondStepVerified` (`apps/api/src/auth/second-step.ts`) is the only place that decides it: Supabase `aal2`, or a claimed, unexpired Passport record for the session. `/gms/me` (`mfaVerified`), the workspace membership guard and both agent-consent checks read it; nothing compares `aal` on its own. The lookup happens only when a check needs it and the session is not already `aal2`. An unreadable record is "not verified".
- 2026-11-11 · The brief said to require `amr` to include `otp`. Passport maps both the emailed code and the authenticator to `otp`, so `otp` does not show an authenticator was used; it adds `mfa` only at `aal2`. The GMS requires `acr: aal2` **and** `mfa`.
- 2026-11-11 · The claim compares SHA-256 digests in the database (an indexed equality), not in constant time in the Worker. The digest is of a 224-bit random token the caller must already hold; timing reveals nothing usable about a preimage.

## Open differences with Passport (need an owner decision)

Found by reading `egeria-corporation/passport` at the time of this build; details in `docs/payments.md`.

- The §14 award routes (`award:write`, `POST/PATCH /passport/funders/{orgId}/awards`) do not exist in Passport yet. The mirror client is behind `awardWrite: false`; no facilitated payment can run end to end until that PR lands.
- Passport has no `GET /passport/funders/{id}` or `send-funds.ach`; readiness check 3 reads `GET …/funders/{orgId}/sources` (`canDebit`).
- Rails are `auto | standard | instant`; `scheduledFor` is refused; memo is capped at 140 characters.
- Passport creates a `held` disbursement itself during a destination change (with `/release` and `/cancel`). The GMS tranche machine from §10.1 has no `releasing → held` transition; it needs one, or the GMS must refuse release earlier.
- `payee.*` webhooks reach only funders linked through `POST …/funders/{orgId}/links`.
- `GET /passport/orgs/{orgId}/profile` is user-session only, so profile-based prefill and eligibility (`profile.*`) cannot use the stored consent token.
- 2026-11-11 — `gms.opengrants.io` is served by the existing Workers and Supabase project (`[env.staging]`), not a second production set — the owner's decision: faster and cheaper for a beta. `gms-staging.opengrants.io` redirects (308). `[env.production]` in the Wrangler files is unused and names the same routes; do not deploy it alongside. Trade-off: no separate place to test a fix.
- 2026-11-11 — The demo data was removed from the hosted database with the owner's approval (all rows except the five global templates; 13 `.example` sign-in accounts). The first attempt also emptied `templates`, because `truncate … cascade` follows the foreign key to `workspaces`; they were restored from `supabase/seed.sql` with the same ids. The landing page's example links now show only in mock mode.
- 2026-11-11 — Platform review fixes (owner: "go ahead and fix the bugs"). The agent consent page moved from `/oauth/consent` to `/consent`: the hosted site routes every `/oauth/` path to the API Worker, so a web page under it could never load; `GET /oauth/consent` on the API redirects old links. Invitation links (`/invitations/accept?token=`) now have a page; before, every invitation email led to "Page not found".
- 2026-11-11 — The design reference boards (`/styleguide/*`) and template previews (`/preview/*`) are routed in mock mode only. They carry the fictional demo content and were public on the live domain; the two in-app links to them are hidden outside mock mode.
- 2026-11-11 — `GET /gms/config` reports `available` (openGrants, assistant, googleWorkspace, mercury, customMcp), each true only when the server has what the connection needs. The web app offers a tab, form or Connect button only where its entry is not false, and says "not available on this installation" otherwise; a connection that cannot work no longer looks like an outage or a working button. `openGrants` is true only with the port and `OPENGRANTS_API_KEY` both present (revisit when discovery moves to the REST API).
- 2026-11-11 — `/gms/me` returns `displayName` (the name on the auth account, else the first part of the address, capitalised) and `signInMethod` (`passport` when the session holds Passport's second step, else `email`). The app greeted people by their email address and told Passport users they signed in by emailed code.
- 2026-11-11 — The funder rail is filtered by role in the web app (reviewers see Dashboard, Applications and Reviews; observers and auditors lose Communications, Approvals and Settings), and someone whose only roles are reviewing is sent to the reviewer portal after sign-in. The API still decides access; this only stops the app offering screens that will refuse.
- 2026-11-11 — The opportunity someone clicked Apply on is kept in the tab's session storage (public handle and slug only) through sign-in, Passport and onboarding, because Passport's return address cannot carry it; Find funding pins it first or says it is not open.
- 2026-11-11 — Removed controls that did nothing rather than leave them inert: the workspace search box, three Help buttons, and footer links to Privacy, Terms and Status pages that do not exist. The sign-in page no longer says "by continuing you agree to the terms": there are no terms to agree to yet.
- 2026-11-11 — Funding search uses the OpenGrants **REST API** with a server-side key, not the hosted MCP (owner's decision). The MCP takes OAuth sign-in only and refused an API key, and the first client's tool names were guesses that did not match the real ones. REST covers search and matching; eligibility checks and alerts are not offered from the GMS until OpenGrants exposes them over REST. Verified against the live API (search and match returned 20 listings each).
- 2026-11-11 — An applicant's Passport access token is cached in the Worker isolate's memory and refreshed by one request at a time (`apps/api/src/services/passport-tokens.ts`); the rotated refresh token is written back with a compare-and-swap on the stored ciphertext. Parallel requests used to spend the same single-use refresh token, which Passport treats as theft and answers by withdrawing the consent. Memory only, not KV: the one KV namespace is the rate limiter and a bearer token does not belong there. Two isolates can still present the same refresh token at once; Passport forgives that for 30 seconds after a rotation (its migration 0057), and the loser of the swap keeps its access token.
- 2026-11-11 — Links into Passport go to `/funders/:id` when the cached Passport record says the organization only makes grants (`organizationKind` custom field), otherwise to `/orgs/:id`; a record cached before Passport published the field falls back to the workspace's kind. An applicant workspace can be linked to a funder-kind Passport organization, so the workspace kind alone is not enough.
- 2026-11-11 — The Passport access token for an applicant consent is stored on `passport_links` (`access_token_enc`, encrypted like the refresh token beside it) with a `token_version` counter (migration 0019). Why: every Worker isolate started with an empty in-memory cache and spent the refresh token to get an access token, about sixty refreshes in seventeen minutes for one link on the hosted site; it held only because Passport forgives a token presented twice within seconds. Now a cold worker reads the stored token, new tokens are written only if `token_version` is unchanged (no ciphertext in a query filter), the loser of that swap adopts the winner's token, and a 401 makes the next call refresh and overwrite the stored copy. The stored token is cleared when the link is revoked. Left to Passport's replay window: two workers that find the token expired at the same instant. An unknown `/gms` route answers 501 and is no longer logged at error level.
- 2026-11-12 — **The GMS can be used without Passport** (owner decision; CLAUDE.md rule changed from "Passport is the identity source" to "Passport is the source of verified identity"). A workspace that has not linked Passport keeps a self-declared profile (`workspaces.profile_source`, `workspaces.self_declared_profile`, migration 0026): always shown as not verified (`verification: { source, level }` on every applicant summary a funder sees and on the funder public page), never served as a CommonGrants organization, and replaced by the Passport record when the workspace links (ledgered as `workspace.profile_replaced_by_passport` with the names of the fields that differed). Facilitated payments, verification levels and organization change requests stay Passport-only. Why: organizations that cannot or will not use Passport could not apply at all. Choices taken where the contract left them open, each the more restrictive reading: the two opportunity options live in `opportunities.publish` (the opportunity's existing options object, no column) and both default to false; a rule on a self-reported `org.*`/`profile.*` fact is marked `selfReported` whether or not the value was present, so a `missing: "pass"` rule cannot pass on it; `profile.*` (Passport's registry-backed Common App profile) counts as Passport-only alongside the level and attestation; fields that "follow Passport" in a form are read-only only for a Passport workspace (an applicant without Passport fills them, prefilled from its profile and marked `self_declared`); letters go to at most five admins when there is no organization address; a self-declared funder's contact address is not published on its public page; email replies into a thread are still accepted only from the Passport record's address; workspace creation is capped at 5 per person and 20 per network address per day (`apps/api/src/lib/rate-limit.ts`, counted only on success; no per-address cap when the request carries no address).
- 2026-11-12 — Security review of the no-Passport feature (NP-01 to NP-17), fixed before launch. A self-declared `contactEmail` is shown and never emailed: letters to a workspace without Passport go to its admins at their sign-in addresses, at most five (otherwise the GMS was a mail relay under a funder's name). Beside a verification badge a Passport workspace is named by its Passport legal name; its own display name comes second as `workspaceName`. Workspace `settings` patches keep only an allow-list of keys (`USER_SETTINGS`); server-owned keys such as `passportPayee` and `assistMonthlyQuota` are dropped. `requirePassport` is checked at every submit as well as at start. A type taken from a self-declared profile is self-reported; all of `org.customFields` and `org.status` are Passport-only. A funder linking Passport takes its legal name and EIN from Passport, or clears the typed ones. Workspace-creation caps are counted in Postgres (migration 0027, one statement per key under a row lock), IPv6 by /64, and forwarded headers are trusted only with `TRUSTED_PROXY`. 0026 (not yet live, edited in place) clears Passport data on workspaces with no Passport organization and checks that a level and a Passport organization go with the Passport source. Tranche recipients, the 990-PF list (a "Verified with Passport" column; `PC` only from a Passport 501(c)(3) record), CommonGrants application `customFields.gms` and the `application.submitted` event carry verification. A self-declared EIN is refused for individuals and for prefixes the IRS never assigns. Unverified funder pages show a banner and their website as unlinked text. Not done: names from before this change on funders already linked keep their stored `legal_name` (no migration rewrites them); CommonGrants `funders.primary.name` falls back to the workspace name when Passport gave none.
- 2026-11-12 — Review F-01: a funder can no longer make an organization its grantee without a relationship. The CSV award import matches a recipient (by EIN, then name) only among applicant workspaces connected to the funder (`connectedApplicants`: a submitted application to it, a live consent to it, or an award it made in the GMS); an award an earlier import attached does not count on its own (`IMPORTED_AWARD_CONNECTS = false`, the one place to relax). Any other row is kept as a named recipient and reported exactly like a name that matches nothing, so the dry run is not a membership test. The grantee directory and detail show Passport's facts (Passport id, legal name, level, payee status, bank name and last four) only while the organization has a live consent to the funder, the rule `sendCommunication` already used; reminders, manual and planned, go only to such organizations. Manual reminders are limited to one per requirement per `MANUAL_REMINDER_INTERVAL_HOURS` (24), answered 429; they are recorded in `reminder_sends` under offsets from 1,000,000 up (no plan can use them), so the unique key lets one through a burst without a migration. Awards are otherwise created only from the funder's own applications (decisions, amendments) and by the operator's `gms import`, so no other route attaches an award to an unrelated workspace.

- 2026-11-10 · Supabase sessions are verified against the project's published signing keys (ES256/RS256, JWKS), with the legacy HS256 secret still accepted; a bearer is treated as a session by its issuer, not its algorithm · new Supabase projects sign sessions asymmetrically, which the first staging deploy showed.
- 2026-11-10 · Staging (`gms-staging.opengrants.io`) is served by a generated front Worker with the web app embedded and a service binding to the API, and `/openapi.json` falls back to the exports bucket · the session's deploy token could not upload static assets or edit zone routes. Production keeps the route layout. See `docs/staging.md`.
- 2026-11-10 · Owner decisions for launch: (1) v1 launches with the funder Google Workspace connector; (2) the assistant is on at launch; (3) consented apps see confirmed Passport profile values only; (4) Passport shares verified representatives with consented apps and the GMS checks signers against them; (5) the bar for go-live is all 15 definition-of-done items passing against real services; (6) the seven partial screens are completed before launch; (7) launch happens without Stripe live mode, so tranches are recorded as paid outside the GMS (`PAYMENTS_FACILITATED=false`) until Passport goes live.
- 2026-11-10 · The GMS client at Passport is to be owned by Egeria Corporation · owner decision. Not done yet: Passport has no organizations, so Egeria Corporation must be claimed there first.

- 2026-11-11 · **Sign in with Passport** (`GET /gms/passport/signin/start` and `/callback`): one trip to Passport signs the person in (OpenID Connect, `openid email`) and links the organization they approve · owner decision; "Continue with Passport" used to be a link to a page that needs a session, so it did nothing for a signed-out visitor. Email-code sign-in is unchanged.
- 2026-11-11 · A Passport sign-in whose verified email matches an existing GMS account signs in to that account · owner decision. Email is already the account key here (the email code proves the same control), so the GMS selects the account by the email Passport marks verified and keeps the Passport user id in the account's `app_metadata.passport_user_id` for reference; it is never used to select an account.
- 2026-11-11 · The callback trusts nothing from the browser: PKCE verifier, nonce and a browser-binding value are sealed in `state` (AES-GCM, `CREDENTIALS_ENCRYPTION_KEY`, ten minutes); the binding must equal a `__Host-` HttpOnly SameSite=Lax cookie set at the start, so a callback URL planted in another browser is refused (login CSRF); the ID token is verified with `jose` against Passport's published keys for issuer, audience (the GMS client), expiry and nonce. Every failure redirects to `/signin?passport_error=<code>` with one of seven codes and no detail.
- 2026-11-11 · The session itself is still Supabase Auth's: after the checks the API asks the Supabase admin API for a one-time magic-link token and redirects to `/auth/passport#token_hash=…`, which the web app redeems with `verifyOtp` · no second session system, and MFA, sessions list and sign-out keep working. The token travels in the URL fragment, which is not sent to servers or logged; the response is `no-store` with `Referrer-Policy: no-referrer`.
- 2026-11-11 · A new person who approves no organization at Passport is not given an account: they are sent back with `no_organization` and a link to claim one. A person who already belongs to a workspace is signed in without linking · applying starts from an organization's record, and an account with nothing to open helps nobody.
- 2026-11-11 · Both sign-in routes share a fixed-window limit of 30 requests per network address per ten minutes (the KV namespace the MCP limiter uses) · they are public and each one makes Passport or Supabase do work.
- 2026-11-11 · The applicant organization link (`linkApplicantOrganization`) is one function used by the consent callback and the sign-in callback · two copies would drift. Identity scopes are never written to `passport_links.scopes`.
- 2026-11-11 · **Accounts have no passwords, and nothing set before an email was proven survives the proof** (migration `0017`, security review). Supabase Auth lets anyone start a sign-up for any address with a password; the account stays unconfirmed, but the password stayed on it and began working once the real owner proved the email by code, magic link or Passport (verified on the hosted project). The GMS only ever signs people in by emailed code or Passport, so a trigger on `auth.users` clears the password on every insert and update, and a second one removes any second factor and session at the moment an email is first confirmed. Both run as the role changing the row (Supabase Auth's own), so they need no extra grant. "Confirm email" must stay on in Supabase Auth (it is on for the hosted project; `supabase/config.toml` and `docs/self-host.md` said off and are corrected): with it off a sign-up is handed a session for an unproven address at once, which no trigger can tell apart from a real one.
- 2026-11-11 · Sign in with Passport **replaces an unconfirmed account instead of adopting it** (deleted, then created fresh and confirmed; if it cannot be deleted nobody is signed in), and **ties an account to the first Passport user that signs in to it**: `app_metadata.passport_user_id` is written once and a different Passport user presenting the same verified email is refused with `passport_error=account_mismatch`. This narrows the owner's "same email, same account" rule to accounts whose email was proven here; email-code sign-in still works for anyone refused.
- 2026-11-11 · **The last hop of Sign in with Passport is bound to the tab that started it.** The button stores a random value in `sessionStorage` and sends it as `hop`; the API seals it in `state` and returns it in the fragment beside the one-time sign-in; `/auth/passport` redeems only when the two match, uses the value up either way, and never redeems in a tab that is already signed in. Without this a link carrying an attacker's own one-time sign-in would silently sign a victim's browser into the attacker's account. A start request without a valid `hop` is refused, so the API's start route cannot be used on its own.
- 2026-11-11 · ID tokens must carry `typ: JWT`, and when Passport's key set names any `oauth-…` key only those keys are used, so no other kind of Passport token or key family can pass as a sign-in. An unknown key id refetches the set once (key rotation). The web app's destination check is the API's allow-list (`RETURN_TO`), held equal by a test. Start and callback are rate-limited apart, per address (`CF-Connecting-IP`, else the first forwarded address); requests with no address share one larger allowance. KV has no atomic increment, so the limit is a brake, not a quota. Not changed: Supabase's one-time token lifetime (an hour, project setting).

## Open differences with Passport (need an owner decision)

Found by reading `egeria-corporation/passport` at the time of this build; details in `docs/payments.md`.

- The §14 award routes (`award:write`, `POST/PATCH /passport/funders/{orgId}/awards`) do not exist in Passport yet. The mirror client is behind `awardWrite: false`; no facilitated payment can run end to end until that PR lands.
- Passport has no `GET /passport/funders/{id}` or `send-funds.ach`; readiness check 3 reads `GET …/funders/{orgId}/sources` (`canDebit`).
- Rails are `auto | standard | instant`; `scheduledFor` is refused; memo is capped at 140 characters.
- Passport creates a `held` disbursement itself during a destination change (with `/release` and `/cancel`). The GMS tranche machine from §10.1 has no `releasing → held` transition; it needs one, or the GMS must refuse release earlier.
- `payee.*` webhooks reach only funders linked through `POST …/funders/{orgId}/links`.
- `GET /passport/orgs/{orgId}/profile` is user-session only, so profile-based prefill and eligibility (`profile.*`) cannot use the stored consent token.
- 2026-11-11 — `gms.opengrants.io` is served by the existing Workers and Supabase project (`[env.staging]`), not a second production set — the owner's decision: faster and cheaper for a beta. `gms-staging.opengrants.io` redirects (308). `[env.production]` in the Wrangler files is unused and names the same routes; do not deploy it alongside. Trade-off: no separate place to test a fix.
- 2026-11-11 — The demo data was removed from the hosted database with the owner's approval (all rows except the five global templates; 13 `.example` sign-in accounts). The first attempt also emptied `templates`, because `truncate … cascade` follows the foreign key to `workspaces`; they were restored from `supabase/seed.sql` with the same ids. The landing page's example links now show only in mock mode.
